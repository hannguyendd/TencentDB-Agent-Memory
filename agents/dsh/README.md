# DeepSeek Harness (dsh)

> agentSource: `dsh` | Protocol: **Anthropic Messages** (v0.2+) / OpenAI Chat (v0.1.x)
>
> To import local history into Memory Hub, see the [Asset Import Guide](./asset-import.md).

> ⚠️ **Major change on 2026-09-29**: starting with dsh v0.2.0-rc.1, the adapter protocol and the configuration entry point have changed.
> The old `~/.dsh/settings.yaml` approach (dsh v0.1.x + setup-proxy.sh) is **obsolete**;
> see Section 1 below for details.

## 0. dsh v0.1 → v0.2 migration (from 2026-09-29)

### 0.1 Configuration comparison

The same task is written completely differently across the two major dsh versions. The configuration generated by the old setup-proxy.sh
**cannot boot at all** in v0.2 (the loader does not recognize the settings.yaml shape, and the plugin id has been renamed).

| Item | dsh v0.1.x (old) | **dsh v0.2+ (current)** |
|---|---|---|
| Config entry file | `~/.dsh/settings.yaml` (top-level plugin section) | `~/.dsh/profiles/web/cordis.patch.yml` (loader patch array) |
| Plugin id | `@deepseek-ai/dsh-llm-deepseek` | `@deepseek-ai/dsh-llm-deepseek-api-key` |
| Upstream protocol | OpenAI Chat Completions | **Anthropic Messages** |
| Request endpoint | `${baseURL}/chat/completions` (no /v1) | `${baseURL}/v1/messages` (/v1 required) |
| Anthropic header | None | `anthropic-version: 2023-06-01` always sent |
| User input carrier | `content: string` (bare text) | `content: [{type:"text",text}, ...]` (anthropic block array) |
| Tool result carrier | `role:"tool" + tool_call_id` (message level) | `role:"user" + content[].type:"tool_result"` (block level) |
| Credential storage | Flat in settings.yaml | `refs:` section of `~/.dsh/.credentials.yaml` (chmod 600 required) |
| Build requirement | `npm install` is enough | Recommended `git pull && pnpm install && pnpm run build` (rc versions iterate fast) |

### 0.2 Companion proxy-side fixes (landed 2026-09-29 → 09-30)

The first category above is dsh upstream changes. The second category is that **proxy-side support had not kept up**, which only surfaced once the first category was fixed and real dsh
v0.2 requests hit the proxy. This round fixed 5 issues in total, already in
`team-proxy@develop_server_team`:

| # | Location | Symptom |
|---|---|---|
| 1 | `src/session/dsh/form.ts` | Only had an openai SSE builder; anthropic clients could not parse the form |
| 2 | `src/session/dsh/form.ts` | ASSET_CONFIRM_YES used a half-width comma while the CB extractor used a full-width one, so they never matched → the form kept popping up after a selection |
| 3 | `src/session/codebuddy/cleaner.ts` | Only recognized openai `role:"tool"+tool_call_id`, not anthropic `role:"user"+tool_result` → team/agent/task stage answers could not be read |
| 4 | `src/agent-adapters/dsh.ts` | `extractUserText` only accepted strings, not anthropic content block arrays → mem commands were not recognized |
| 5 | `src/anthropicHandler.ts` | 3 `buildMemResponse` return points were missing the `maybeFixDshStreamTail` wrapper → dsh's strict parser reported `STREAM_CLOSED` |

Items 3, 4, 5 are edge cases on the chain where dsh reuses the CB state machine; the old proxy code assumed the openai wire shape;
anthropic branches have now been added. CC/CB/WB/opencode/codex are completely unaffected.

### 0.3 Three steps to migrate from v0.1 to v0.2

1. **Pull the latest dsh**: `cd deepseek-harness && git pull && pnpm install && pnpm run build` (at least `v0.2.0-rc.1`)
2. **Back up + swap config**:
   ```bash
   TS=$(date +%Y%m%d_%H%M%S)
   cp ~/.dsh/settings.yaml    ~/.dsh/settings.yaml.bak.$TS 2>/dev/null   # back up the old setup
   cp ~/.dsh/.credentials.yaml ~/.dsh/.credentials.yaml.bak.$TS
   # Rewrite cordis.patch.yml + the .credentials.yaml refs section per §1.1 / §1.2
   ```
3. **Proxy side at least at develop_server_team @2026-09-30** (includes the 5 fixes in the table above). An old proxy version
   running dsh v0.2 will hit, in order: form cannot be parsed → form keeps popping up → answers cannot be read → mem has no effect → mem reports STREAM_CLOSED.

## 1. Client configuration (dsh v0.2+)

Starting with dsh v0.2, the configuration entry moved from `~/.dsh/settings.yaml` to the cordis
patch under the **profile directory**, and credentials are stored separately in `~/.dsh/.credentials.yaml`. The plugin's internal id also changed from
`dsh-llm-deepseek` to `dsh-llm-deepseek-api-key` (the default login variant).

### 1.1 Profile patch file

`~/.dsh/profiles/web/cordis.patch.yml` (the profile name defaults to `web`, used by `dsh web` at startup):

```yaml
- id: llm-deepseek
  name: "@deepseek-ai/dsh-llm-deepseek-api-key"
  config:
    apiKeyEnv: PROXY_USER_KEY
    # ⚠️ No /v1 — the dsh anthropic adapter internally builds `${baseURL}/v1/messages`
    # See the dsh source packages/llm/llm-deepseek/src/messages-api.ts:14-17
    baseURL: http://<proxy-host>:8096/dsh/<spaceId>
    reasoningEffort: high
    models:
      - id: deepseek-v4-pro
        name: DeepSeek V4 Pro
        contextWindow: 128000
        maxTokens: 8192

- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: deepseek-official
    model: deepseek-v4-pro
    reasoningEffort: high
```

### 1.2 Credential file

`~/.dsh/.credentials.yaml` (permissions strictly required: chmod 600):

```yaml
version: 1
refs:
  PROXY_USER_KEY: <your business user_key, obtained from the platform>
```

### 1.3 Permission requirements (validated when dsh starts)

```bash
chmod 700 ~/.dsh
chmod 600 ~/.dsh/.credentials.yaml
```

### 1.4 Request path

**dsh v0.2+ uses the Anthropic protocol**; the adapter hardcodes `${baseURL}/v1/messages` +
the `anthropic-version: 2023-06-01` header (source `packages/llm/llm-deepseek/src/adapter.ts:120-131`).
The proxy side hits:

- `POST /dsh/:spaceId/v1/messages` ← main path for dsh v0.2+
- `POST /dsh/:spaceId/v1/messages/count_tokens` ← auxiliary endpoint

The old openai path (for dsh v0.1.x users only) is also kept for compatibility:
- `POST /dsh/:spaceId/v1/chat/completions`
- `POST /dsh/:spaceId/chat/completions`

### 1.5 Start & verify

```bash
cd /path/to/deepseek-harness
git pull                 # at least v0.2.0-rc.1 (from 2026-09)
pnpm install && pnpm run build
pnpm dsh web --no-open --port 3081 --host 127.0.0.1
# → dsh web: http://127.0.0.1:3081/?token=xxx
```

Open that URL in a browser and send "hi"; the proxy will return the session-init form (see Section 3).

## 1.6 Desktop client configuration (DeepSeek Harness Desktop)

> Verified on 2026-10-08: the dsh desktop `0.2.1-alpha.1` (Electron shell + Node Host subprocess) is **100% equivalent** to the CLI/Web version at the LLM
> protocol layer — the `packages/llm/*` code is shared, and the Electron shell takes no part in
> any outbound LLM fetch. So the **proxy supports the desktop version with zero changes**; only the UI configuration entry needs to be the right one.

### 1.6.1 There are three configuration entries; only the second works

On the desktop "Settings → Models" page, **three cards** are shown for DeepSeek-type providers:

![dsh desktop model settings](./imgs/desktop-model-settings.png)

| Card | Internal plugin | Protocol | header | **Proxy compatibility** |
|---|---|---|---|---|
| ① DeepSeek account | `@deepseek-ai/dsh-llm-deepseek-account` | Anthropic Messages | Does not send `x-deepseek-harness-session-id` (passes through the account token; not our integration shape) | ❌ Not applicable |
| ② **DeepSeek (deepseek-official)** ← red box | `@deepseek-ai/dsh-llm-deepseek-api-key` | Anthropic Messages | **Full set of `x-deepseek-harness-*` headers** (user-id / session-id / compact) | ✅ **Configure only this one** |
| ③ Custom settings / Add model provider | `@deepseek-ai/dsh-llm-pi-ai` | OpenAI Chat / Responses / Anthropic (pick one) | ⚠️ **Sends no `x-deepseek-harness-*` headers** (the pi-ai adapter filters them out) | ❌ session_id lost → proxy session-init form cannot pop up |

### 1.6.2 Why only the second works (wire evidence)

On desktop, as with CLI/Web, **only when going through the `llm-deepseek-api-key` adapter (the "DeepSeek deepseek-official" card)
do request headers carry the full set of dsh identification signals**:

```http
POST /dsh/<spaceId>/v1/messages HTTP/1.1
authorization: Bearer <proxy user_key>
anthropic-version: 2023-06-01
x-deepseek-harness-user-id: <anonymous UUID>
x-deepseek-harness-session-id: session-<uuid>      ← ★ the entry criterion for proxy session-init
x-deepseek-harness-compact: 1                      ← only sent on compaction requests
user-agent: deepseek-harness/0.2.1-alpha.1 (+...)
```

With the third "Custom settings" card, the underlying adapter is `llm-pi-ai` (source
`packages/llm/llm-pi-ai/src/adapter.ts:204-212`), whose `requestHeaders`
**keeps only attribution headers and filters out the whole `x-deepseek-harness-*` family**. So on the proxy side:

- `conversationId=null` → the `sessionInit` condition `conversationId && !isAuxiliary` is not met
- → `injectedSkipped=true` → the entire session-init form **never pops up**
- → everything is passthrough; injection / archiving / mem commands are all skipped

This is the same pitfall as the CLI-side rule "do not attach the pi-ai plugin in `~/.dsh/profiles/web/cordis.patch.yml`".

### 1.6.3 Configuration steps

1. Click the "**Edit**" button on the red-box card
2. **API key**: enter the `user_key` issued by the platform (exactly the same key as `PROXY_USER_KEY` in the CLI-side `.credentials.yaml`)
3. **Expand "Custom settings"** (collapsed by default), and fill in baseURL:
   ```
   http://<proxy-host>:8096/dsh/<spaceId>
   ```
   - ⚠️ **Do not include `/v1`** — the dsh anthropic adapter internally builds `${baseURL}/v1/messages` (source
     `packages/llm/llm-deepseek/src/messages-api.ts:14-17`); including it would double up into `/v1/v1/messages`
   - For `<spaceId>`, fill in the memory instance id assigned by the platform (usually `default` or `mem-<...>`)
4. Click "**Save**"

### 1.6.4 Verification

Send "hi"; the proxy should pop up the `ask_user_question` form. Check the proxy logs:

```
[identity] userId=... keyId=... custom=[x-api-key,x-deepseek-harness-session-id,x-deepseek-harness-user-id]
[injection-debug] conversationId=session-<uuid> sessionKey=session-<uuid>
                  agentSource=dsh kind=main dshHeadless=false
                  sessionInitEnabled=true injectedSkipped=false ✓
pipeline.forward.start upstream=https://api.deepseek.com/anthropic/v1/messages
pipeline.forward.done status=200
```

Key fields:
- `custom=[...x-deepseek-harness-session-id,x-deepseek-harness-user-id]` ← only present when the right entry is used
- `agentSource=dsh` ← determined from the `/dsh/<spaceId>` path segment
- `injectedSkipped=false` ← session-init condition met; the form will pop up

Counter-example (when using the third "Custom settings" card):

```
[identity] custom=[x-api-key,x-stainless-arch,x-stainless-lang,...]   ← pi-ai's headers, no dsh family
agentSource=dsh injectedSkipped=true                                   ← ★ the form does not pop up
```

**Fully transparent to the proxy** (research source: `docs/dsh-recon/2026-10-08-dsh-desktop-verification`):

| Dimension | Desktop | CLI/Web | Proxy impact |
|---|---|---|---|

### 1.6.6 Proxy-side setup

By default the desktop version does not send requests to `copilot.tencent.com` — deepseek-official goes to
`https://api.deepseek.com/anthropic`. So in `proxy-service.config.yaml`, `upstream.agents`
**must explicitly configure an upstream for `dsh`**, otherwise it falls back to the outer default `/v2` and returns 404 (verified 2026-10-08):

```yaml
upstream:
  agents:
    dsh:
      # dsh v0.2+ llm-deepseek-api-key adapter uses Anthropic Messages,
      # proxy anthropic joinUrl automatically appends /v1 → .../anthropic/v1/messages
      url: https://api.deepseek.com/anthropic
      apiKey: sk-<deepseek official key>   # with apiKey set → proxy overrides the client Bearer before forwarding
```


## 2. Session ID

| Priority | Header |
|--------|--------|
| 1 | `x-deepseek-harness-session-id` |
| 2 | `x-session-id` |

**Condition for sending this header** (dsh source `packages/llm/llm-deepseek/src/adapter.ts:129`):
sent only if the caller (agent loop) passes `options.sessionId`; not sent when `undefined`. The dsh Web UI
main conversation normally passes it every turn, and auxiliary requests such as `title-gen` / `compaction` also carry it (the compaction scenario
additionally carries `x-deepseek-harness-compact: 1`).

⚠️ **Pitfall**: if the baseURL points to `/claude-code/<spaceId>` (piggybacking on the CC route) instead of
`/dsh/<spaceId>`, the proxy takes the CC form/extractor branch for `agentSource=claude-code`,
and the `ask_user_question` schema mismatch makes the client report "unknown tool". Always use the dedicated `/dsh/*`.

## 3. Session Init (session initialization / Form)

### 3.1 Mechanism

dsh officially auto-attaches
`@deepseek-ai/dsh-tool-ask-user` in preset scenarios (web-app / cordis / standard, etc.) (source `packages/interaction/tool-ask-user/src/index.ts`),
adding an `ask_user_question` tool to the main conversation's tools array. The proxy directly reuses this native tool name
to forge a fake tool_use SSE:

- Tool name: **`ask_user_question`** (snake_case, completely different from CC's PascalCase `AskUserQuestion`)
- Tool call id prefix: `call_dsh_session_init_`
- Transport: **Anthropic SSE** (v0.2+, `message_start → thinking → tool_use → message_stop`),
  or OpenAI chat.completion.chunk (v0.1.x compatibility, dispatched by `FormData.protocol`)

### 3.2 ask_user_question schema (hard dsh constraints, incompatible with CC)

```jsonc
{
  "questions": [
    {
      "id": "asset_confirm",       // ← required by dsh, echoed in answer
      "question": "本次对话是否要关联团队资产?",
      "header": "关联资产",
      "options": [
        { "label": "是，关联团队资产", "description": "..." },
        { "label": "否，本次不关联",   "description": "..." }
      ],
      "multi_select": false          // ← snake_case, not multiSelect
    }
  ]
}
```

The tool_result is returned (under the anthropic protocol the dsh client puts it in a `type:"tool_result"` block inside the
`content[]` of a `role:"user"` message):
```jsonc
{
  "answers": [
    { "id": "asset_confirm", "selected": ["是，关联团队资产"], "custom": "..." }
  ]
}
```

`selected[]` is an **array of the selected option label strings** (not indexes). `custom` is the free text the user typed in
"Other" (also the fallback criterion for the skip keyword).

### 3.3 State machine

Reuses the CB state machine (`src/session/codebuddy/init.ts`):

```
uninitialized → pending_asset_confirm → pending_team_select →
pending_agent_task → (optional) pending_task_select → initialized
```

- CB / WB / dsh / opencode / codex share this state machine
- Differences (form shape / transport protocol / tool name) are re-rendered in `result.response` in a
  `agentSource === "dsh"` branch in `src/session/index.ts`
- dsh's standalone files are in `src/session/dsh/` (form.ts / __tests__/)

### 3.4 Pagination

dsh's `ask_user_question` UI has **no limit on the number of options** (source
`packages/interaction/tool-ask-user/src/index.ts` + the UI QuestionComposer both just map and
render), so the dsh form **does not paginate** and stuffs all teams/agents/tasks in. By contrast, CC has a hard limit of <=4 options
and must paginate.

### 3.5 Headless Bypass

dsh has a unique headless bypass:

- Check the `body.tools` array
- If non-empty but **does not contain** `ask_user_question` → the proxy decides it is headless and skips session-init entirely, passing through

This lets dsh work normally in direct API calls / batch mode (custom tools but no interactive tool).

### 3.6 thinking block required (anthropic branch)

DeepSeek's official anthropic-compatible endpoint **strictly validates**, in thinking mode, that historical assistant messages must
carry a `thinking` block, otherwise 400 `The content[].thinking in the thinking mode must be
passed back to the API`. The fake session-init response (Anthropic branch) generated by the proxy
unconditionally emits an empty thinking + placeholder signature block; see the comments on
`THINKING_SIGNATURE_PLACEHOLDER` in `src/session/dsh/form.ts`.

The OpenAI branch has the same problem, handled with a `reasoning_content` placeholder (see `REASONING_PLACEHOLDER` in the same file).

### 3.7 Skipping Session Init

Three ways:
1. Headless bypass (no `ask_user_question` in tools) → skipped automatically
2. The user types "跳过" / "skip" via the `custom` field
3. Choose "否，本次不关联" at asset_confirm

## 4. Request classification

dsh uses its own classification logic (`src/agent-adapters/dsh.ts`):

| Type | Detection | Handling |
|------|----------|------|
| **compact** | `x-deepseek-harness-compact: 1` header | Auxiliary request, skip injection |

| **main** | Everything else | Full pipeline |

## 5. User text extraction

A dsh message's content is usually a **plain string** (typed directly by the user) or an **anthropic content block array**
(when the user message carries a tool_result). The cleaner first scans for a tool_result block whose `tool_use_id` matches the
`call_dsh_session_init_` prefix, and falls back to the text block of the last user message.
See `getLastUserMessageText` in `src/session/codebuddy/cleaner.ts`.

## 6. Injected Profile

After session-init completes, the proxy appends to the end of the anthropic request's `system` section:

```xml
<agent_skills>...</agent_skills>
<user_memory>...</user_memory>
<session_context>...</session_context>
<available_skills>...</available_skills>
<tdai_profile_memory>...</tdai_profile_memory>
```

Injection point: anthropic `body.system` (dsh v0.2+). The old openai branch injects into `messages[0].content`
(appended inside the system message string, dsh v0.1.x compatibility).

## 7. Special behaviors

- **Protocol**: v0.2+ = **Anthropic Messages** (hard-sends `anthropic-version: 2023-06-01`);
  v0.1.x = OpenAI Chat. Determined by dsh's upstream adapter; the proxy dispatches by the request path
  `/v1/messages` vs `/v1/chat/completions` to `handleAnthropicMessages` or
  `handleChatCompletions`
- **Handler**: v0.2+ uses `src/anthropicHandler.ts` (shared with CC); v0.1.x uses
  `src/handler.ts` (shared with CB)
- **Client fingerprint headers**:
  - `user-agent: deepseek-harness/*`
  - `x-deepseek-harness-user-id` (sent unconditionally; anonymous id or logged-in account id)
  - `x-deepseek-harness-session-id` (sent only if `options.sessionId` is present)
  - `x-deepseek-harness-compact: 1` (compaction scenario)
- **Thinking mode**: assistant messages carry a `thinking` block (anthropic) or a `reasoning_content`
  field (openai); the proxy's fake session-init response must satisfy the upstream hard validation (see 3.6)
- **ask_user_question schema is completely incompatible with CC**: snake_case tool name, required id, returns an array
  (see 3.2)

## 10. FAQ

**Q: What causes the client error `unknown tool "AskUserQuestion"`?**
A: dsh v0.2 only recognizes the snake_case `ask_user_question` and does not recognize CC's PascalCase
`AskUserQuestion`. Check that the baseURL points to `/dsh/<spaceId>` (not `/claude-code/<spaceId>`);
only then will the proxy use the dsh form builder and produce the correct tool name.

**Q: Session init keeps looping on the "Associate assets?" form?**
A: Three possibilities:
1. A stale pending_asset_confirm state in Redis is stuck → start a new dsh session
2. The proxy version is too old → needs at least the dsh anthropic patch from develop_server_team @2026-09-29 or later
3. The dsh baseURL uses `/claude-code/*`, so agentSource is recognized as CC → switch to `/dsh/*`

**Q: dsh and CB share a state machine; will dsh sessions leak into CB's?**
A: No. The state machine code is shared (one CB init.ts), but the session key includes an `agentSource`
prefix (`dsh:<sid>` vs `codebuddy:<sid>`), so they are fully independent in Redis.

**Q: When does the dsh headless bypass trigger?**
A: When `body.tools` is non-empty but does not contain `ask_user_question`. Typical scenario: dsh in API mode
calling directly (custom tools but no user interaction).

**Q: Why does dsh need thinking / reasoning_content placeholders?**
A: DeepSeek's official anthropic/openai-compatible endpoints strictly validate assistant messages in thinking mode
— they must have a thinking block / reasoning_content field. The session-init
form response generated by the proxy is also an assistant message and must carry this field (the value may be empty/placeholder; the content has no effect on the model
because the fake session-init never actually goes through the model).

**Q: I am still on dsh v0.1.x with the old `~/.dsh/settings.yaml`; does it still work?**
A: Yes. The proxy side retains the OpenAI branch (when FormData.protocol is unspecified or "openai", it uses the
openai chat.completions SSE builder). But we strongly recommend upgrading dsh to v0.2+ and using the anthropic
protocol, which is the officially promoted direction.

**Q: The client reports `DeepSeek Messages stream ended before message_stop / STREAM_CLOSED`?**
A: The SSE parser of the dsh v0.2 `llm-deepseek-api-key` adapter (source
`packages/llm/llm-deepseek/src/translate.ts:165`) strictly requires `\n\n` to end an event,
while the old implementation of the proxy's mem-command shared response builder only appended a single `\n` at the end (CC /
the official Anthropic SDK parser is lenient and does not break, but dsh's strict implementation does). The fix: the `maybeFixDshStreamTail` wrapper in `anthropicHandler.ts` only appends one
`\n` after stream responses with `agentSource==="dsh"`,
leaving the shared builder untouched byte for byte — CC / CB / WB / opencode / codex are unaffected.
If it still occurs after upgrading to develop_server_team @2026-09-30, run `grep -n maybeFixDshStreamTail
src/anthropicHandler.ts` to check whether the wrapper covers the `buildMemResponse`
return point you hit (currently all 4 call sites are covered: pre-intercept unsupported / main mem-command / session
not initialized / _resetFlowResult confirmation response).
