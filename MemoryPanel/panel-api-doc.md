# MemoryPanel API Documentation

> Service: MemoryPanel (control panel), port `8125`

---

## 1. Common Conventions

### 1.1 Base URL and Port

| Item | Value |
|---|---|
| Base URL | `/api/v1` (except `/health`) |
| Port | 8125 |
| Method | Except for `GET /health` and `GET /api/v1/meta/instances`, **all are `POST`** (RPC style) |
| Content-Type | `application/json` |

### 1.2 Authentication

Most business endpoints depend on the following headers (validated by the middleware `validatePanelMetaHeaders`):

| Header | Required | Description |
|---|---|---|
| `x-tdai-service-id` | Yes | Instance ID, used to locate the target kernel gateway (`instanceRegistry.resolve`) |
| `x-tdai-user-key` | Yes* | The current user's key, used by the kernel side's `auth/verify` to look up the caller identity |
| `x-request-id` | No | Passed through to the response envelope `request_id`, for log correlation |

> `*` Exceptions: `POST /meta/auth/verify` (no user-key needed, since it is itself the key verification); `POST /knowledge/status-callback` (S2S callback, no browser headers); `GET /health`, `GET /meta/instances` (no authentication).

### 1.3 Response Envelope

All business endpoints uniformly return:

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { }
}
```

| Field | Type | Description |
|---|---|---|
| code | number | `0` for success; non-zero for failure |
| message | string | Always `"ok"` on success; on failure an uppercase-underscore error enum (a stable contract; the frontend branches on it) |
| request_id | string | Request ID, from `x-request-id` or generated by the server |
| data | any | Business data; `null` on failure |

> Exceptions: `GET /health` and `GET /meta/instances` **do not return the envelope** and return bare JSON directly (see §3.1).

### 1.4 HTTP Status Mapping

Mapping rule for `HTTP status = envelope.code`:

| envelope.code | HTTP status |
|---|---|
| `0` | `200` |
| `400 ~ 599` | Same as `code` |
| Otherwise | `502` |

### 1.5 Pagination Conventions

- Kernel list endpoints default to `DEFAULT_PAGINATION = { limit: 20 }`: **if the frontend calls a `meta/*` list action directly without passing limit, only the first 20 items are returned**.
- Panel-layer aggregation/business endpoints (such as `chat-memory/*`, `knowledge/*/team-assets`) already paginate internally to pull everything, so the frontend need not page.
- `task/list-with-agents` has a `limit` upper bound of 200; when omitted the kernel returns the default 20 items, but the response `limit` field echoes 50 (a known inconsistency, see §3.5).

### 1.6 Idempotency Conventions

- Knowledge create endpoints (`wiki/create`, `code-graph/create`) rely on idempotent reuse of the same name/resource: a repeated create returns the existing resource rather than an error.
- Create-type `meta/*` actions (`user/create`, `team/create`, `agent/create`, `task/create`) check for duplicates first at the Panel layer, and a duplicate name returns `409` with a message (in Chinese in the original implementation).

### 1.7 Request ID Chain

`x-request-id` (optional) → passed through into the envelope `request_id` → also carried when forwarding to the kernel, for cross-service log correlation.

## 3.2 Metadata Transparent Proxy

### POST /meta/*

Forwards `{ action, ...payload }` to the kernel `/v3/meta/{action}`, passing the envelope through as-is. This is the Panel's unified entry to the kernel metadata plane (user/team/agent/task/asset/acl, etc.).

**Authentication**: `x-tdai-service-id` + `x-tdai-user-key` (only `auth/verify` is exempt from user-key).

**Forwarding semantics**:
- The request body is passed through whole to the corresponding kernel action; the response envelope is returned as-is.
- The last path segment is the action name (e.g. `POST /meta/agent/list` → kernel `agent/list`).
- Actions outside the allowlist return `404 UNKNOWN_META_ACTION`; `agent-fixed-asset/*` returns `501 NOT_IN_SCOPE` (such operations are invoked directly inside the Panel business routes, see §3.4/§3.10).

**List of open actions (53)**:

| Entity | action |
|---|---|
| user | create, create-with-key, get, delete, list |
| user-key | create, list, get, revoke, update |
| team | create, get, update, delete, list |
| team-member | add, remove, list, get |
| agent | create, get, update, delete, list, archive, set-default-template, get-default-template |
| task | create, get, update, delete, list, archive |
| task-agent | link, unlink, list |
| participation-log | append, list |
| asset | create, get, update, delete, list, list-accessible, touch-usage |
| acl | grant, revoke, list, check |
| auth | verify |
| instance-quota | get |
| config/user | get, set |

**Not open (`501 NOT_IN_SCOPE`)**: `agent-fixed-asset/set`, `agent-fixed-asset/list`, `agent-fixed-asset/list-with-detail`, `agent-fixed-asset/summary-by-agents`.

**Special handling at the Panel layer (not pure passthrough)**:

| action | Behavior |
|---|---|
| `user/create`, `user/create-with-key`, `team/create`, `agent/create`, `task/create` | Check for duplicates by name/username/title first; a duplicate name returns `409` with a message (in Chinese in the original implementation) |
| `agent/set-default-template` | **Not forwarded to the kernel**; the Panel writes the template file locally; requires `system_admin` permission, otherwise `403 permission_denied`; a missing `team_id`/`template` returns `400 INVALID_PARAM` |
| `agent/get-default-template` | **Not forwarded to the kernel**; the Panel reads the template file locally |
| `team-member/add` | After success, asynchronously copies template assets for the default Agent (best-effort) |
| `user/list` | Hides the internal `knowledge-service` billing user |

**Example** (`agent/create`):

```json
// Request
POST /api/v1/meta/agent/create
{ "team_id": "t_1", "owner_user_id": "u_1", "name": "Release Assistant" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "agent_id": "agt_xxx", "name": "Release Assistant" }
}
```

## 3.3 Skill Data-Plane Transparent Proxy

### POST /skill/*

Forwards `{ action, ...payload }` to the kernel `/v3/skill/{action}`, passing the envelope through as-is.

**Authentication**: `x-tdai-service-id` + `x-tdai-user-key` (mandatory; skill needs the owner identity).

**Differences from `/meta/*`**:
- The Skill data plane has independent storage (`skill_id` prefix `skl-`): readable within the team, writable by the owner agent.
- Identity fields (`user_id` / `team_id` / `agent_id` / `task_id`) go in the **body**, not in headers.
- Pagination uses nested `pagination.{limit, offset}`, with the body passed through as-is.

**List of open actions (15)**:

| action | Description |
|---|---|
| create | Create a skill |
| update | Full update |
| patch | Partial update |
| delete | Delete |
| get | Get one |
| list | Paginated list |
| search | Search |
| versions | Version list |
| files/write | Write a file |
| files/remove | Remove a file |
| files/read | Read a file |
| listing | Directory listing |
| extract | Extract |
| export | Export |
| conversation/add | Conversation append (the main skill-extraction path; added to the allowlist in 2026-08) |

**Errors**: an unknown action returns `404 UNKNOWN_SKILL_ACTION`.

**Example** (`list`):

```json
// Request
POST /api/v1/skill/list
{
  "user_id": "u_1",
  "team_id": "t_1",
  "filters": { "status": ["active"] },
  "pagination": { "limit": 50, "offset": 0 }
}

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "skill_id": "skl_1", "name": "code-review", "owner_agent_id": "agt_1" } ],
    "total": 1
  }
}
```

## 3.4 Chat-Memory

> Unified output structure of a memory block (MemoryBlock):

| Field | Type | Description |
|---|---|---|
| id | string | Asset ID (`chat_memory-{team}-{agent}` or self-created `mem-xxx`) |
| title | string | Block title |
| summary | string | Summary (currently placeholder text) |
| uploaded_by_user_id | string | Owner user ID |
| updated_at_ms | number | Update time (ms epoch) |
| layer_counts | object | `{ L0_messages, L1, L2, L3 }` (currently placeholder, all 0) |
| scope | string | `team` / `private` |
| agent_id | string | Associated agent (returned by some endpoints) |

### POST /chat-memory/team-assets

List of memory assets shared with the team (`visibility=team`, regardless of owner). **Note: the MemoryBlock returned by this endpoint does not contain the `scope` field** (everything in the team-assets tab is semantically already shared).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | Yes | Team ID |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| items | MemoryBlock[] | Team-shared memory blocks (without `scope`) |
| total | number | Total count |

**Example**

```json
// Request
{ "team_id": "t_1" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "chat_memory-t_1-agt_1", "title": "Release Assistant", "summary": "0 L1 · 0 L2 · 0 L3" } ],
    "total": 1
  }
}
```

### POST /chat-memory/agent-fixed

List of `chat_memory`-type fixed-asset bindings under the specified Agent. **Visible to the Agent owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| agent_id | string | Yes | Agent ID |

**Response** `data`: `{ items: MemoryBlock[], total }`, where each item carries `scope` (`team`/`private`) so the frontend can gray out entries "set to private by the owner".

**Errors**: `MISSING_AGENT_ID`, `INVALID_USER_KEY`, `AGENT_NOT_FOUND`, `NOT_YOUR_AGENT`.

### POST /chat-memory/my-agents

"My asset allocation" tab: returns all Agents I own, each Agent corresponding to one memory block (`block.id = chat_memory-{team}-{agent}`).

**Request body**: `{ team_id: string }`

**Response** `data`: `{ items: MemoryBlock[], total }`, each item carrying `agent_id` and `scope` (from the visibility of that agent's own memory).

**Errors**: `MISSING_TEAM_ID`, `INVALID_USER_KEY`.

### POST /chat-memory/mine

List of memory assets owned by me (the owner).

**Request body**: `{ team_id: string }`

**Response** `data`: `{ items: MemoryBlock[], total }`.

**Errors**: `MISSING_TEAM_ID`, `INVALID_USER_KEY`.

### POST /chat-memory/create

Create a standalone memory asset (UserAsset, `mem-xxx`).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | Yes | Team ID |
| title | string | Yes | Title, ≤ 200 characters |
| scope | string | No | `team` (default) / `private` |
| description | string | No | Description |

**Response** `data`: `MemoryBlock` (`id` is the newly created `mem-xxx`).

**Errors**: `MISSING_TEAM_ID`, `INVALID_TITLE`, `INVALID_USER_KEY`.

**Example**

```json
// Request
{ "team_id": "t_1", "title": "Product requirements notes", "scope": "team" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "id": "mem_xxx", "title": "Product requirements notes", "scope": "team" }
}
```

### POST /chat-memory/import

Import historical conversations into the L0 of the Agent's memory pool (via the data plane `/v3/conversation/add`; no new asset is created).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | Yes | Team ID |
| agent_id | string | Yes | Target Agent |
| messages | object[] | Yes | `[{ role, content, ts? }]`, ≤ 100 items |
| session_id | string | No | Session ID, auto-generated as `imported-{ts}` by default |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| imported | boolean | Always `true` |
| block_id | string | `chat_memory-{team}-{agent}` |
| session_id | string | The actual session |
| accepted_count | number | Number of items successfully written |

**Errors**: `MISSING_TEAM_ID`, `MISSING_AGENT_ID`, `MISSING_MESSAGES`, `TOO_MANY_MESSAGES`, `NO_VALID_MESSAGES`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`.

**Example**

```json
// Request
{
  "team_id": "t_1",
  "agent_id": "agt_1",
  "messages": [ { "role": "user", "content": "Help me look at this bug" } ]
}

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "imported": true, "block_id": "chat_memory-t_1-agt_1", "accepted_count": 1 }
}
```

### POST /chat-memory/patch-scope

Change memory visibility (team ↔ private).

**Request body**: `{ block_id: string, scope: "team" | "private" }`

**Response** `data`: `{ updated: true, id, scope }`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_SCOPE`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`.

### POST /chat-memory/set-agent-fixed

Batch-set an Agent's fixed memory (atomic validation + a single full set).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| agent_id | string | Yes | Target Agent |
| team_id | string | Yes | Team ID |
| block_ids | string[] | Yes | IDs of the memory blocks to bind (including its own `chat_memory-{team}-{agent}`) |

**Response** `data`: `{ updated: true, agent_id, block_ids }`.

**Errors**: `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `IMPORT_LIMIT_EXCEEDED`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `TEAM_MISMATCH`, `ASSET_NOT_SHARED`.

### POST /chat-memory/allocate

Allocate (borrow) a shared memory block to the specified Agent. Includes a "borrow ≤ 2" validation.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| agent_id | string | Yes | Target Agent |
| team_id | string | Yes | Team ID |

**Response** `data`: `{ allocated: true, agent_id, block_id }`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `TEAM_MISMATCH`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `ASSET_NOT_SHARED`, `IMPORT_LIMIT_EXCEEDED`; a repeated allocation returns `409` with a message (in Chinese in the original implementation); allocating an agent's own `chat_memory-{team}-{agent}` to itself again returns `400` with a message (in Chinese: "cannot allocate the Agent's own memory to itself again").

**Example**

```json
// Request
{ "block_id": "chat_memory-t_1-agt_2", "agent_id": "agt_1", "team_id": "t_1" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "allocated": true, "agent_id": "agt_1", "block_id": "chat_memory-t_1-agt_2" }
}
```

### POST /chat-memory/unbind

Unbind borrowed memory from an Agent.

**Request body**: `{ block_id: string, agent_id: string, team_id: string }`

**Response** `data`: `{ unbound: true, agent_id, block_id }`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `CANNOT_UNBIND_SELF_CHAT_MEMORY`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `BINDING_NOT_FOUND`.

### POST /chat-memory/layer

Layered lazy loading of memory content. Resolves team/agent from `block_id` and then calls the kernel data plane.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | Yes | `L0` / `L1` / `L2` / `L3` |
| limit | number | No | Valid values `(0, 200]`; if omitted, ≤0, or >200, falls back to 50 (not a clamp, unlike the clamp semantics of task/search) |
| offset | number | No | Default 0 |
| before_ts | string | No | L0 cursor pagination (ISO8601; to page, pass the time of the last item of the previous page) |
| time_start | string | No | Time filter start (L0/L1 only) |
| time_end | string | No | Time filter end (L0/L1 only) |
| path | string | No | File path to specify when reading a single L2 item |

**Data source per layer**: L0 → `/v3/conversation/query`; L1 → `/v3/atomic/query`; L2 → `/v3/scenario/ls` (list) / `/v3/scenario/read` (with `path`); L3 → `/v3/core/read`.

**Response** `data`: `{ layer, items, total, limit, offset }`, with each `items` entry structured as:

| Field | Type | Description |
|---|---|---|
| id | string | Entry ID (L3 is always `"core"`) |
| title | string | Title (L0 is role@session, L1 is the type, L2 is the path, L3 is always `"core memory"`) |
| role | string? | L0 only: message role (`user`/`assistant`/`tool`, etc.) |
| body | string | Content |
| tags | string[] | Tags |
| refs | string[] | References (currently always empty) |
| created_at | string | Time (ISO) |

**Read permission**: any one of owner / `visibility=team` / borrowed by an agent under the caller; otherwise `403 ASSET_NOT_ACCESSIBLE`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `ASSET_NOT_ACCESSIBLE`, `RANGE_TOO_LARGE` (time filter range too large, VDB cannot support it), `LAYER_FETCH_ERROR`.

**Example** (L1)

```json
// Request
{ "block_id": "chat_memory-t_1-agt_1", "layer": "L1", "limit": 20, "offset": 0 }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "layer": "L1",
    "items": [ { "id": "rec_1", "title": "atomic", "body": "Release next Monday", "tags": [], "refs": [] } ],
    "total": 1,
    "limit": 20,
    "offset": 0
  }
}
```

### POST /chat-memory/clear

Clear the full contents of several memories in one click, keeping the assets themselves (ownership/bindings/ACL unchanged). **Asset Owner only**.

**Request body**: `{ memory_ids: string[] }` (≤ 100 after deduplication).

**Response**: passes through the result of the kernel `/v3/chat-memory/clear`.

**Errors**: `MISSING_MEMORY_IDS`, `TOO_MANY_MEMORY_IDS`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `CLEAR_FAILED`.

### POST /chat-memory/layer-delete

Batch deletion from an L0/L1 list. **Asset Owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | Yes | `L0` / `L1` |
| message_ids | string[] | Used for L0 | Message IDs, ≤ 5000 |
| session_ids | string[] | Used for L0 | Session IDs, ≤ 100 |
| ids | string[] | Used for L1 | Record IDs, ≤ 5000 |

**Response**: passes through the result of the kernel `/v3/conversation/delete` or `/v3/atomic/delete` (including `deleted_count`).

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `TOO_MANY_IDS`, `MISSING_IDS`, `LAYER_DELETE_FAILED`.

### POST /chat-memory/layer-update

Edit the content of a single memory layer. **Asset Owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | Yes | `L1` / `L2` / `L3` |
| id | string | Required for L1/L2 | L1 record primary key / L2 file path |
| content | string | Yes | New content |
| summary | string | No | L2 summary |

**Data source per layer**: L1 → `/v3/atomic/update`; L2 → `/v3/scenario/write` (automatically strips the META header); L3 → `/v3/core/write`.

**Response**: passes through the result of the corresponding kernel write endpoint.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `MISSING_CONTENT`, `MISSING_ITEM_ID`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `LAYER_UPDATE_FAILED`.

### POST /chat-memory/search

Layered keyword search (agent-level cross-session recall).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | No | `L0` / `L1`, default `L1` |
| query | string | Yes | Search term |
| limit | number | No | Default 30, max 100 |
| type | string | No | L1 type filter |

**Response** `data`: `{ items, total }`, with each `items` entry containing `score` (relevance); the L1 `id` can be used directly for `layer-update`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_QUERY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `ASSET_NOT_ACCESSIBLE`, `SEARCH_FAILED`.

**Example**

```json
// Request
{ "block_id": "chat_memory-t_1-agt_1", "layer": "L1", "query": "release" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "rec_1", "title": "atomic", "body": "Release next Monday", "score": 0.92 } ],
    "total": 1
  }
}
```

Aggregates `task/list` + batch `task-agent/list`, returning tasks and their associated agents in one call, eliminating the frontend N+1 (otherwise 2N+1 requests would be needed).

**Upstream**: `meta/task/list`, `meta/task-agent/list`.

**Request body**

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| team_id | string | Yes | — | Team ID |

| offset | number | No | 0 | Offset |
| status | string | No | — | Filter by status |
| title | string | No | — | Title filter |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| items | TaskWithAgents[] | Task list, each containing an `agents` sub-array |
| total | number | Total count |
| limit | number | The actual limit this time |
| offset | number | The actual offset this time |

**Example**

### 4.2 Summary of Error message Enums

> `message` is a stable contract and the frontend branches on it; adding an error code requires updating this table accordingly.
>
> Note the three exceptions to the `message` format (all assembled by the Panel, not pure enums):
> 1. **Data-plane failure class** (`LAYER_FETCH_ERROR` / `CLEAR_FAILED` / `LAYER_DELETE_FAILED` / `LAYER_UPDATE_FAILED` / `SEARCH_FAILED`): the actual value is `"<CODE>: <err.message>"` (with a `: details` suffix), so the frontend should use `startsWith(CODE)` rather than exact equality matching.
> 2. **The 400 of `POST /knowledge/status-callback`**: `message` is a lowercase English sentence (`"wiki_id and progress fields are required"` / `"knowledge_id, type, status are required"`), not an enum. This endpoint is an S2S callback not consumed directly by the frontend and can be ignored.
> 3. **Chinese-sentence class** (`respondControlError` stuffs in Chinese directly, not an enum, and `startsWith(CODE)` cannot match it either): the `meta/*` create duplicate-check 409 ("already exists with the same name ... please change the name and retry"), the `chat-memory/allocate` duplicate allocation 409 ("this memory has already been allocated to that Agent"), and allocating to oneself 400 ("cannot allocate the Agent's own memory to itself again"). The frontend must fall back on the message text or HTTP status, and cannot branch on a CODE enum.
