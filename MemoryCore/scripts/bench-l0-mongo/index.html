Conclusion: the serial numbers are entirely dominated by the 39ms cross-region RTT and do not reflect database capability.

Serial single-document inserts reach only 23.6/s, yet the server spends just 1.9ms: the other 39ms is network round trip. Once concurrency is raised and the RTT is amortized, single-document inserts reach 2,184/s (92x) and queries reach 940/s (40x). There are only two real bottlenecks: index maintenance cost at the 100M scale (writes), and mongot concurrency (BM25 queries).

Why latency barely changes up to concurrency 32

From concurrency 1 to 32, p50 stays around 42ms (RTT + 1.9ms server time) while throughput grows linearly by 28x, which means this range simply fills the pipe and uses the otherwise idle RTT; the server is not stressed at all. Only beyond 64 does p50 start climbing (50 → 100ms), which is when the server actually starts queueing. In other words: cross-region only adds a fixed latency per operation and does not cap total throughput.

2. Effect of batch size

Concurrency is fixed at 8 and only the insertMany batch size changes. This explains why production code goes through insertL0Batch instead of per-document upserts.

batch=1000 has the highest throughput, but the tail latency cost is large

Going from batch 100 to 1000 raises throughput by only 34% (14.7k → 19.8k), while per-batch p99 rises from 148ms to 889ms. For online write paths batch=100 is the better trade-off; batch=1000 suits offline bulk loading only.

The decay comes from index maintenance, not the network

Throughput falls from 24,245/s to ~930/s, a 25x decay, while RTT stays constant throughout. At 95M documents, per-batch (1000 docs) latency reaches p50 8,295ms and p99 12,175ms: each batch takes over 8 seconds. At the same time, currentOp on the server shows 8 insertMany operations running in parallel, so client concurrency is saturated; the slowness is on the server: the maintenance cost of the B-tree plus the mongot inverted index at 100M documents.

It peaks at concurrency 8 (52 QPS); adding more concurrency lowers throughput and latency explodes (p50 reaches 3,093ms at concurrency 128). The cause is that besides paging it also runs a countDocuments, which is a heavy scan at the tenant level over 100M documents.

Recommendation

Split the total out: use an estimate, cache the count, or switch the frontend to "load more" without showing the total page count. This change alone can raise paging from 52 QPS to the same order as sessionReplay (~650 QPS).

6. Conclusions and caveats

It holds up

100M messages were written with 0 errors, the $search index is usable, and business queries all reach hundreds of QPS under concurrency. The data volume itself is not a problem.

Answering "how high can a single hop go"

Single-document inserts (batch=1) reach 2,184 docs/s at concurrency 256 on an empty collection, 92x the serial 23.6/s. The serial number is so low purely because every operation waits for a 39ms round trip while the server spends only 1.9ms. As long as the client is willing to run concurrently, cross-region has almost no effect on total throughput.

The two real limits

Write side: index maintenance cost that decays as the collection grows (24k/s → 930/s). When loading historical data, consider creating the collection first and the $search index afterwards, to avoid maintaining the inverted index while writing.
Read side: mongot BM25 queries cap at 215 QPS, the lowest of all read paths; capacity planning should use this number.
