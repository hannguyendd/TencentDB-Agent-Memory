# v3 API Documentation · Volume 1 MemoryCore

> Service: MemoryCore (memory kernel), port `8420`
> This volume covers all `/v3/*` interfaces exposed by MemoryCore. For MemoryKnowledge (`/v3/wiki`, `/v3/code-graph`, etc.) see Volume 2; for MemoryProxy see Volume 3.
> Maintenance convention: interface changes (added/changed fields/changed error codes) must update this document in the same PR.

---

## 1. Common Conventions

### 1.1 Service and Port

| Item | Value |
|---|---|
| Service | MemoryCore (memory kernel gateway) |
| Port | 8420 |
| Method | All `POST` (v3 is RPC style, no GET) |
| Content-Type | `application/json` |
| Health check | `GET /health` (**not v3**, no auth, returns bare JSON `status/version/uptime/stores/services`, outside the scope of this document) |

### 1.2 Response Envelope

All v3 interfaces return uniformly:

```json
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { } }
```

| Field | Type | Description |
|---|---|---|
| code | number | `0` for success; non-zero for failure. **Note**: failure codes of the skill module are 5-digit numbers (see §1.6) |
| message | string | Fixed `"ok"` on success; an error description on failure (format see §1.6) |
| request_id | string | Request ID, from `x-request-id` or generated by the server |
| data | any | Business data; usually absent or null on failure |

### 1.3 Pagination Conventions

- Data-plane list/query interfaces: `limit` defaults to `20` with an upper bound of `100`, `offset` defaults to `0` (`paginationSchema`).
- Meta list interfaces: `limit` defaults to `20` with an upper bound of `100`, `offset` defaults to `0` (`DEFAULT_PAGINATION`); the output is uniformly `{ items, total, limit, offset }`.
- skill `list`: `limit` upper bound `1000`; skill `search`: `top_k` upper bound `50`.
- knowledge `list`: `pagination.limit` upper bound `1000` (`knowledgeListRequestSchema`, same as skill list).
- memory-prompt / generation-log list: `limit` defaults to `20` with an upper bound of `100`.

### 1.4 Auth Layers

v3 interfaces fall into four layers by auth method (all require `Authorization: Bearer <KERNEL_AUTH_TOKEN>` as the Layer 1 gateway gate, not enforced when `apiKey` is not configured):

| Layer | Route scope | Additional auth |
|---|---|---|
| Data plane | `/v3/conversation·atomic·scenario·core/*`, `/v3/skill/*`, `/v3/knowledge/*`, `/v3/chat-memory/*`, `/v3/memory-prompt/*`, `/v3/memory-generation-log/*` | `x-tdai-service-id` (instance ID) |
| Metadata plane | `/v3/meta/*` | `x-tdai-service-id` + `x-tdai-user-key` (user key; `auth/verify` is exempt from user-key) |
| Internal ops plane | `/v3/internal/meta/*` | Bearer only, **does not parse** user-key |
| Instance destroy | `/v3/instance/destroy` | Bearer apiKey only (v1 style, ops interface) |

> Isolation fields note: the `team_id / agent_id / user_id / task_id` of data-plane interfaces can be passed via **body or Header** (`x-tdai-team-id` / `x-tdai-agent-id` / `x-tdai-user-id` / `x-tdai-task-id`), with body taking precedence. The v3 data plane **enforces** team + agent + user triple isolation (missing values fall back to the `default` bucket).

### 1.5 Error Code Semantics (common to the data plane)

| code | Meaning |
|---|---|
| 400 | Invalid parameters (missing ID, mutually exclusive fields, empty input) |
| 401 | Auth failed |
| 403 | Ownership consistency check failed (e.g. `(team_id, agent_id)` does not form a valid ownership, `task_id` does not belong to `team_id`) |
| 404 | Resource does not exist or does not belong to the current call context (existence is not exposed) |
| 409 | Concurrency contention timeout |
| 422 | Schema passes but business rules fail |
| 429 | Rate limit / quota exceeded |
| 500 | Internal error |
| 503 | Dependency unavailable (LLM / storage / VDB) |

### 1.6 Error message Formats (three kinds, important)

The failure `message` format differs between modules, so the frontend must handle them separately:

| Module | message format | HTTP code characteristics | Example |
|---|---|---|---|
| meta / internal-meta | `"{error_code}: {detail}"` (error_code is uppercase snake_case) | Standard 4xx/5xx | `"team_not_found: not found: t_1"` |
| skill | `SkillCoreError.message` verbatim | **5-digit number** (40001, etc.) | `"SKILL_NOT_FOUND: ..."` |
| Data plane / knowledge / chat-memory / memory-prompt / generation-log | Plain text or plain uppercase enum | Standard 4xx/5xx | `"Knowledge not found"`, `"MEMORY_PROMPT_NOT_FOUND"`, `"Store not available"` |

## 3. Interface Details

## 3.1 L0–L3 Data Plane (18)

> Memory layers: L0 raw conversations (conversation), L1 memory atoms (atomic, including episodic/persona/instruction types), L2 scene files (scenario), L3 core persona (core).
> All interfaces accept the 4 ID isolation fields (`team_id/agent_id/user_id/task_id`, body or Header).
> Delete interfaces such as `conversation/delete` and `atomic/delete` trust Bearer + `x-tdai-service-id` and do no user-level auth (consistent with the validation before the panel forwards requests).

### POST /v3/conversation/add

Write L0 raw conversation messages. After a successful write, the L1 extraction pipeline is triggered asynchronously (`notifyPipeline`).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| session_id | string | Yes | Business session ID |
| messages | object[] | Yes | 1–100 items, `{ role: "user"\|"assistant", content: 1–8192 chars, timestamp?, recorded_at? }` |
| team_id / agent_id / user_id / task_id | string | No* | Isolation fields (*v3 enforces team+agent+user; missing values fall back to the default bucket) |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| accepted_ids | string[] | IDs of accepted messages |
| accepted_versions | string[] | Same order as accepted_ids, newly created ones are fixed to `v1` |
| total_count | number | Total accepted |

**Example**

```json
// Request
{ "session_id": "sess_1", "messages": [ { "role": "user", "content": "Help me look at this bug" } ] }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "accepted_ids": ["msg_1"], "accepted_versions": ["v1"], "total_count": 1 }
}
```

### POST /v3/conversation/query

Paginated query of L0 messages.

**Request body**: `session_id?`, `limit?` (default 20 / max 100), `offset?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ messages: ConversationItem[], total }`, ConversationItem = `{ id, version, role, content, timestamp?, recorded_at?, session_id?, team_id?, user_id?, agent_id? }`.

### POST /v3/conversation/search

Keyword search of L0 messages.

**Request body**: `query` (1–2048), `limit?` (default 5 / max 100), `session_id?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ messages: (ConversationItem & { score })[] }`.

### POST /v3/conversation/delete

Batch delete L0 by message_ids or session_ids.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| message_ids | string[] | One of the two | ≤5000 items |
| session_ids | string[] | One of the two | ≤100 items |
| session_id | string | No | @deprecated, use session_ids instead |

**Response** `data`: `{ deleted_count: number }`.

**Errors**: `400` (at least one of the two must be provided).

### POST /v3/conversation/count

L0 count (**v3 only, no v2 entry**).

**Request body**: `session_id?`, `time_start?`, `time_end?`.

**Response** `data`: `{ total: number }`.

---

### POST /v3/atomic/update

Update a single L1 memory atom (version auto-increments).

**Request body**: `id`, `content` (≤8192), `background?` + isolation fields.

**Response** `data`: `{ id, version, updated_at }`, where `version` is a **string** `"v{n}"` (e.g. `"v2"`).

> ⚠️ Inconsistent version type: `update` returns the string `"v{n}"`, but `query`/`search` return a **number** (`r.version ?? 0`). The root cause is in the code (`generated/types.ts` declares `string "v1"`, but `v2-schemas.ts` overrides it to `number`); the doc cannot satisfy both, so the frontend must handle each interface separately.

### POST /v3/atomic/query

Paginated query of L1.

**Request body**: `type?` (episodic/persona/instruction), `time_start?`, `time_end?`, `limit?`, `offset?` + isolation fields.

**Response** `data`: `{ items: AtomicDetail[], total }`.

**AtomicDetail** fields:

| Field | Type | Description |
|---|---|---|
| id | string | Atom ID |
| version | number | Current version number (**query/search return a number**; note `update` returns the string `"v{n}"`, an inconsistent type) |
| type | string | `episodic` / `persona` / `instruction` |
| background | string? | Background |
| content | string | Body text |
| created_at / updated_at | string | ISO time |
| team_id / agent_id / user_id / task_id | string? | Isolation fields |

**Example**

```json
// Request
{ "type": "episodic", "limit": 20, "offset": 0 }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "rec_1", "version": 1, "type": "episodic", "content": "Release next Monday", "created_at": "2026-08-20T00:00:00Z", "updated_at": "2026-08-20T00:00:00Z" } ],
    "total": 1
  }
}
```

### POST /v3/atomic/search

Keyword search of L1.

**Request body**: `query` (1–2048), `limit?` (default 5 / max 100), `type?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ items: (AtomicDetail & { score })[] }`.

### POST /v3/atomic/delete

Batch delete L1 by id.

**Request body**: `ids: string[]` (≤5000).

**Response** `data`: `{ deleted_count: number }`.

### POST /v3/atomic/count

L1 count (**v3 only**).

**Request body**: `type?`, `time_start?`, `time_end?`.

**Response** `data`: `{ total: number }`.

---

### POST /v3/scenario/ls

L2 scene file list (one-shot full listing, no pagination).

**Request body**: `path_prefix?` (empty/omitted = recursive listing from the root) + isolation fields.

**Response** `data`: `{ entries: ScenarioEntry[], total }`.

**ScenarioEntry**: `{ path, summary?, version, team_id?, agent_id?, created_at, updated_at }` (directories have `version=0`, path ends with `/`).

### POST /v3/scenario/read

Read a single L2 file.

**Request body**: `path` (relative path, with path-traversal check), `version?` + isolation fields.

**Response** `data`: `{ path, version?, content, created_at, updated_at }`. **A non-existent file returns 200 with content/created_at/updated_at null (not 404)**.

### POST /v3/scenario/write

Write an L2 file (META header is stripped automatically).

**Request body**: `path`, `content`, `summary?` + isolation fields.

**Response** `data`: `{ path, version, updated_at }`.

### POST /v3/scenario/rm

Delete an L2 file/directory.

**Request body**: `path` (ending with `/` = delete directory, otherwise delete a single file) + isolation fields.

**Response** `data`: none (`successEnvelope(undefined)`).

### POST /v3/scenario/count

L2 count (**v3 only**).

**Request body**: `path_prefix?`.

**Response** `data`: `{ total: number }`.

---

### POST /v3/core/read

Read L3 core memory (persona.md).

**Request body**: `version?` + isolation fields (body may be empty).

**Response** `data`: `{ content, version?, team_id?, agent_id?, created_at, updated_at }`. **A non-existent file returns 200 with content null**.

### POST /v3/core/write

Write L3 core memory (Scene Navigation and leading/trailing whitespace are stripped automatically).

**Request body**: `content` + isolation fields.

**Response** `data`: `{ version, updated_at }`.

### POST /v3/core/count

L3 count (**v3 only**).

**Request body**: `{}` (empty object).

**Response** `data`: `{ total: number }`.

## 3.2 Skill (17)

> Skill data plane has independent storage (`skill_id` prefix `skl-`), readable within the team, writable by the owner. Identity fields go in the body.
> Failure codes are **5-digit numbers** (see §1.6); the error code mapping is in appendix §4.2.

### POST /v3/skill/create

Create a skill (after success, automatically registers a meta_asset and binds it to the owner agent).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| name | string | Yes | ≤64 chars, must equal frontmatter.name |
| content | string | Yes | Full text of SKILL.md |
| resources | object[] | No | ≤100 items, `{ path ≤512, content, encoding: "utf-8"\|"base64", mime_type?, is_executable? }` |
| metadata | object | No | Custom metadata |
| team_id / agent_id / user_id / task_id | string | See below | Write interfaces require team+agent+user to be provided |

> Constraint: `agent_id` must be namespaced under `team_id` (having an agent requires having a team).

**Response** `data`: `SkillSummary` (see the unified note at the end of §3.2).

**Errors**: `40001` (parameter/frontmatter mismatch), `42201` (duplicate name), `4291` (quota exceeded), `50304` (consecutive skill_id collisions).

**Example**

```json
// Request
{ "team_id": "t_1", "agent_id": "agt_1", "user_id": "u_1", "name": "code-review", "content": "---\nname: code-review\n---\n# Code Review" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "skill_id": "skl_1", "name": "code-review", "version": 1, "status": "active", "owner_user_id": "u_1", "owner_agent_id": "agt_1", "team_id": "t_1" }
}
```

### POST /v3/skill/update

Full update (optimistic lock).

**Request body**: `skill_id`, `expected_version` (≥1), `content` + id fields.

**Response** `data`: `SkillSummary`.

**Errors**: `40901` (stale version, data carries `current_version`), `40401`, `40301`.

### POST /v3/skill/patch

Partial replace (optimistic lock, string patch).

**Request body**: `skill_id`, `expected_version`, `old_string`, `new_string`, `replace_all?` + id fields.

**Response** `data`: `SkillSummary`.

**Errors**: `40901`, `42202` (patch not unique), `40401`.

### POST /v3/skill/delete

Physical delete (**changed 2026-07, previously soft delete**): deletes all versions + clears storage, cascading cleanup of meta_asset / ACL / agent bindings.

**Request body**: `skill_id`, `expected_version`, `team_id?` + id fields.

**Response** `data`: `{ skill_id, archived: boolean }`; `archived` semantically means "delete succeeded", `deleted > 0` (**not an archived state**; the field is reused for real deletes too).

**Errors**: `40401`, `40901`, `40301`, `40302`.

### POST /v3/skill/get

Fetch details by skill_id (content / manifest optional).

**Request body**: `skill_id`, `version?`, `include_content?` (default true), `include_manifest?` (default true) + id fields.

**Response** `data`: `SkillSummary + { content?, manifest?, content_hash?, storage_dir? }`.

**Errors**: `40401`.

### POST /v3/skill/get-by-name

Fetch details uniquely by `(team_id, agent_id, skill_name)` (so an agent gets the full text in one call during tool invocation).

**Request body**: `team_id` (required), `agent_id` (required), `skill_name` (≤64), `version?`, `include_content?`, `include_manifest?`.

**Response** `data`: same as `get`.

**Errors**: `40401` (a missing name is always returned uniformly, without revealing whether the name or the id is missing).

### POST /v3/skill/list

Paginated list (returns only active by default; archived must be passed explicitly via `filters.status`).

**Request body**: `filters?` (`{ owner_agent_id?, name_prefix?, status?: ["active"\|"archived"] }`), `pagination?` (`{ limit ≤1000, offset }`) + id fields.

**Response** `data`: `{ items: SkillSummary[], total }`.

### POST /v3/skill/search

Search skills.

**Request body**: `query` (≤2048), `top_k?` (≤50), `mode?` (bm25/embedding/hybrid), `scope?` (="team" means team scope without owner filtering) + id fields.

**Response** `data`: `{ items: (SkillSummary & { score, snippet })[] }`.

### POST /v3/skill/versions

Version list.

**Request body**: `skill_id`, `pagination?` + id fields.

**Response** `data`: `{ items: (SkillSummary & { is_expired })[], total }`.

**Errors**: `40401` (skill does not exist).

### POST /v3/skill/files/write

Write script/resource files.

**Request body**: `skill_id`, `expected_version`, `files` (1–100, same structure as resources in create) + id fields.

**Response** `data`: `SkillSummary`.

### POST /v3/skill/files/remove

Delete files.

**Request body**: `skill_id`, `expected_version`, `paths` (1–100) + id fields.

**Response** `data`: `SkillSummary`.

### POST /v3/skill/files/read

Read a single file.

**Request body**: `skill_id`, `path`, `version?`, `encoding?` + id fields.

**Response** `data`: `{ content, version, size_bytes, encoding, ... }`.

### POST /v3/skill/export

Export a skill (zip).

**Request body**: `skill_id`, `version?`, `format?` (only "zip") + id fields.

**Response** `data`: `{ version, file_count, total_bytes, ... }`.

**Errors**: `41301` (too large).

### POST /v3/skill/listing

Generate the `<available_skills>` injection block (for the agent prompt).

**Request body**: `query?` (≤2048), `char_budget?` (0–64000, default 8000) + id fields.

**Response** `data`: `{ mode: "full"\|"search", listing: string, hits: [{ skill_id, version, name }] }`.

### POST /v3/skill/extract

direct-trigger manually archives a session slice once (equivalent to one standalone skill extraction).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| user_id / team_id / agent_id | string | Yes | None may contain `\|` |
| messages | object[] | Yes | 1–500 items, `{ role: user\|assistant\|tool_call\|tool_result\|system, content, timestamp?, tool_name?, tool_call_id? }` |
| session_id | string | No | Generated with the `sx-` prefix if omitted |
| space_id | string | No | Falls back to auth.serviceId if omitted |
| task_id / reason / options | — | No | `options.max_iterations` (1–64) |

**Response** `data`: `{ ok: true, task_id, archived_at_ms, archive_key }`.

### POST /v3/skill/conversation/add

Called synchronously at the end of each conversation round, performing concatenation + threshold check + archiving (main skill extraction path).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| session_id / user_id / team_id / agent_id | string | Yes | None may contain `\|` |
| messages | object[] | Yes | 1–500 items (role same as extract; `tool_call`/`tool_result` must carry tool_name+tool_call_id) |
| space_id / task_id | string | No | — |

**Response** `data`: `{ status: "ok"\|"archived", archived?: { task_id, archived_at_ms, archive_key, reason } }`, `archived.reason ∈ tool_calls\|bytes\|compressed\|oversize`.

**Errors**: `40001` (schema/validation), `404` (module not enabled), `50001`.

### POST /v3/skill/conversation/force-archive

Manually force-archive the current session buffer (skipping the threshold).

**Request body**: `space_id`, `user_id`, `team_id`, `agent_id`, `session_id` (all required), `reason?` (≤2000), `task_id?`.

**Response** `data`: `{ status: "empty" \| "archived", task_id?, archived_at_ms?, archive_key?, message? }`.

## 3.4 Chat-Memory (1)

### POST /v3/chat-memory/clear

Clear the **content** (L0/L1/L2/L3) of several memories while **keeping the assets** (ownership/binding/ACL unchanged).

> Auth: Bearer + `x-tdai-service-id` is treated as a trusted admin-level credential, **with no user-level Owner check** (the Owner check is done before the panel forwards the request).

**Request body**: `memory_ids: string[]` (1–100, auto-deduplicated and empties removed).

**Response** `data`

| Field | Type | Description |
|---|---|---|
| items | object[] | Clear result for each memory |
| all_cleared | boolean | true if all succeeded |

**items[] fields**: `memory_id`, `cleared`, `l0_deleted`, `l1_deleted`, `profile_deleted`, `reason?`, `retryable?`, `attempts?`.

**Errors**: `400` (schema), `503` (store/storage/metadata unavailable); a single memory failure does not fail the whole call and is written as `cleared=false` in `items[]`.

**Example**

```json
// Request
{ "memory_ids": ["chat_memory-t_1-agt_1"] }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "memory_id": "chat_memory-t_1-agt_1", "cleared": true, "l0_deleted": 10, "l1_deleted": 3, "profile_deleted": 1 } ],
    "all_cleared": true
  }
}
```

## 3.5 Memory-Prompt (7)

> Memory prompt management (L1/L2/L3 three-layer prompts); `layer` takes lowercase `l1`/`l2`/`l3`.

### POST /v3/memory-prompt/create

Create a prompt.

**Request body**: `name` (≤100 chars), `layer` ("l1"\|"l2"\|"l3"), `prompt` (≤10000 chars).

**Response** `data`: `{ memory_prompt_id: "mp-xxx", version: 1, created_at_ms }`.

**Errors**: `409` (PROMPT_LIMIT_EXCEEDED, per-instance limit 500).

### POST /v3/memory-prompt/get

Three modes (mutually exclusive):
1. `memory_prompt_id` → returns a single prompt (non-active returns 404).
2. `layer` + (`team_id`/`agent_id`) → resolves the effective prompt (returns the built-in fallback if none).
3. `layer` only → returns a list `{ items }`.

**Request body**: `memory_prompt_id?`, `team_id?`, `agent_id?`, `layer?`, `limit?` (default 20), `offset?`, `time_order?` (default desc).

**Errors**: `404` (MEMORY_PROMPT_NOT_FOUND).

### POST /v3/memory-prompt/update

Update name/prompt.

**Request body**: `memory_prompt_id`, `name?`, `prompt?` (at least one).

### 3.7.12 Auth (1)

### POST /v3/meta/auth/verify

Validates user_key and returns the caller identity. **Exempt from user-key** (it is itself the key validation, on the `V3_NO_USER_KEY_ROUTES` allowlist, going through the handler rather than the auth middleware).

**Request body**: `{ user_key: string }` (`authVerifySchema`; a missing user_key goes through Zod validation → `400`).

**Response** `data`: `{ valid: boolean, user: UserPublic | null }` (**nested structure, not flat**).

- Valid key: `{ valid: true, user: { user_id, user_type, username, created_at } }`
- Invalid key: `{ valid: false, user: null }` (**HTTP is still 200, code=0, no 401 is returned**)

> ⚠️ The frontend must check `data.valid` and **must not handle an invalid key via a 401 branch**. `401 unauthorized: invalid_user_key` is the behavior of **other meta interfaces** going through the auth middleware (`x-tdai-user-key` header validation), not the behavior of `auth/verify` itself.

**Example**

```json
// Request
{ "user_key": "tk_xxx" }

// Response (valid)
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { "valid": true, "user": { "user_id": "usr_1", "user_type": "normal", "username": "zhangsan", "created_at": "2026-08-20T00:00:00Z" } } }

// Response (invalid key; note code is still 0)
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { "valid": false, "user": null } }
```
